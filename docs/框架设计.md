## 0. 旧版问题诊断

旧版 `素晴TRPG规则书.html` 的可用性问题（来自代码审查）：

| 问题 | 现状 | 后果 |
|---|---|---|
| 数据与视图耦合 | 50 万字符内容以 HTML 字符串塞在一个 `rulebookData` JS 数组里 | 无法按字段查询（比如"列出祭司全部4MP以下技能"做不到），改一处要动整块字符串 |
| 一次性渲染 | 116 个小节全部 innerHTML 注入 | DOM 巨大、滚动找不到位置、导航默认全部展开更显乱 |
| 无实体模型 | 技能/装备/怪物都是"带表格的段落" | 无法做筛选、排序、卡片、对比 |
| 搜索弱 | 只按标题/关键词过滤导航项 | 搜"驱散"找不到具体规则 |
| 模组无位置 | 只有一篇模组塞在章节数组里 | 以后加模组只能继续往数组里塞 |
| 校对成果无法落地 | 核对发现 ~120 处错误但无处可修（改字符串=重排版） | — |

**核心结论：重制的本质不是换皮肤，是把内容从"HTML字符串"变成"结构化数据 + 查询界面"。**

## 1. 设计目标

1. **查询 3 秒到达**：玩家桌上问"XX技能什么效果"，3 次点击 / 一次 Ctrl+K 内出答案。
2. **阅读体验**：规则书章节连续阅读 + 悬浮目录 + 搜索高亮，不比 PDF 差。
3. **GM 友好**：怪物卡一屏多张、数值醒目、可快速展开；陷阱/任务/速查表集中在 GM 区。
4. **模组可扩展**：新模组 = 拷一个文件夹 + 改一行清单，界面自动长出来。
5. **保持零安装使用习惯**：构建产物仍是"双击就能打开"的单文件，可以直接拷给别人。
6. **数据可信**：本次 6 份核对报告的已确认错误，在数据管道里一次性修正，并留 fix-log。

## 2. 技术栈选型（权衡与结论）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 沿用单文件 HTML + 原生 JS | 零构建 | 数据不可维护、无组件化、筛选/搜索全手写、DOM 一次性渲染卡 | ❌ 重蹈覆辙 |
| **B. Vue 3 + Vite SPA → 构建为单文件** | 组件化 UI、数据/视图分离、结构化 JSON、生态成熟、构建产物仍可双击打开 | 源码层需要 Node + `npm run build`（使用层仍零安装） | ✅ **选用** |
| C. Tauri / Electron 桌面应用 | 真·本地文件、SQLite、可出 exe | 需要 Rust/打包链、体积大、分享不便 | ❌ 对"查询+阅读"需求过重 |
| D. Nuxt/Astro 静态站生成 | SEO | 无服务端需求，SEO 无意义 | ❌ 复杂度纯增 |

**最终栈：**

```
Vue 3（组合式 API）+ Vite
├── vue-router          页面路由（阅读/资料库/模组）
├── FlexSearch          前端全文搜索（中文 bigram 分词，数据量 2MB 内无压力）
├── 自写 CSS 设计令牌    亮/暗双主题（沿用现有 Solarized 审美），不用重型 UI 库
├── vite-plugin-singlefile  构建产物 = 单个 dist/index.html（图片为独立文件夹，相对路径引用）
└── Python 数据管道     scripts/build_data.py：xlsx / PDF文本 / 旧HTML → 结构化 JSON + 校验 + fix-log
```

**为什么坚持"构建成单文件"**：你现在的使用方式是"文件夹拷走、双击打开"，跑团环境经常没网。`file://` 直开对 ES Module 有 CORS 限制，所以用 singlefile 插件把 JS/数据全部内联进一个 index.html——**源码是干净的模块化工程，产物保持单文件**，两头兼顾。以后加模组就是 `npm run build` 一条命令。

**语言**：JS（不上 TypeScript，降低你后续自己维护的门槛；数据合法性靠管道里的校验脚本保证）。

**模组清单** `manifest.json`：

```json
{
  "dataVersion": "2026-11-07",
  "modules": [
```

### 5.3 数据管道与纠错落库

```
来源（只读）                          管道                     产物
─────────────────────────          ────────────────         ─────────────
法术表.xlsx (官方+AR2E技能)   →  build_data.py  ──────→  skills/*.json
旧HTML sections.json (正文)   →  (解析+清洗+       ────→  rulebook/*.json
英文PDF文本 (校对准据)         →   修错)            ────→  items/enemies/…
核对报告.md (高/中错误清单)    →  fix_log.yaml     ────→  修正后数据+审计记录
```

管道内置两类校验：**数字列完整性**（每行必填字段非空，杜绝 MP 缺失重演）与**引用有效性**（模组引用的 enemyId、前置技能 id 必须存在）。核对报告里所有"高严重度已确认"条目在管道中以 `fix_log.yaml` 显式修正——比如治愈写死 `cost:4, effect:3d6+CL×3`、平局规则写死"反应方优先"、陷阱七条效果逐一回填——而不是靠手改 HTML。

## 6. 搜索设计

- **两级**：导航树即时过滤（标题级）+ Ctrl+K 全文搜索（内容级，FlexSearch bigram 索引，构建时由数据生成）。
- 全文结果带**分组与字段高亮**（技能名/效果/页码），支持 `4MP 祭司` 这类字段词命中。
- 阅读视图内搜索：命中小节列表 + 进入后逐处高亮跳转。

## 9. 角色卡导出（M3.5，用户确认需求）

向导创建完成后，导出**A4 横版、共 2 页**的可打印角色卡，版式复刻用户现有中文角色卡（原版：reddit KonosubaTabletop "improved autocalculating PDF character"，中文制作者：B站 黑白隔阂）：

**第 1 页**（分区沿用原卡配色）：
- 标题区 + 角色名称/玩家名称/年龄/性别/已用经验点数
- 种族/职业/角色等级
- 角色外观（插画位 + 身高/发色/眼色/发型/肤色）
- 生命值/魔力值/祝福值（含使用次数）
- 能力值表：力量/灵巧/敏捷/智力/感知/精神/幸运 × 基础能力值/能力值加成/职业等级/技能等/检定(2d6)
- 战斗判定表（红）：命中(灵巧)/攻击力/闪避(敏捷)/物理防御/魔法防御/行动点(敏捷+感知)/移动力(力量+5)
- 特殊检定表（橙）：侦测陷阱(感知)/解除陷阱(灵巧)/感知威胁(感知)/辨识敌人(智力)/魔法检定(智力)
- 装备表（右手/左手/头部/身体/其他防具/饰品/合计，含全部修正列）
- 所持物品×2 + 可携带重量 + 金钱(KE)
- 人生轨迹（出身/境遇/目标）+ 作弊(开挂) + 生活方式（绿）

**第 2 页**：4 张技能大表（蓝×2 / 橙 / 绿），列：技能|等级|时机|检定|目标|范围|消耗|最大SL|效果|页码参考——按技能类别自动填充（职业/种族/通用/其他）。

**技术实现**：HTML+CSS 打印模板（`@page { size: A4 landscape; margin: 0 }`），浏览器"打印→另存 PDF"即得成品；向导数据单向填充；页脚保留原版署名行。所有数值由应用按官方公式自动计算（属性加成=÷3、行动点=敏捷+感知、移动力=力量+5、HP/MP=职业表+成长），用户可手动覆盖任意格。

**术语校准**：现卡第 7 项属性作「魅力」，官方为「精神(MND)」；导出版按官方术语（用户现卡如需保持可切换）。

## 8. 待确认事项（评审用）

1. **GM 实时工具（M4）要不要提前**：先攻/HP 追踪器对跑团很实用，但会显著增加工作量；建议 M1-M3 先落地，M4 看使用反馈。
2. **图片策略**：旧版插图（人物立绘等）是否全部迁入？涉及产物体积（单文件内联 JS 数据，图片走外置文件夹）。
3. **社区自制内容（AR2E/Watson/Haru）**：默认收录并打来源徽章（沿用现方案），还是默认隐藏、开关打开？——影响技能库默认视图。
4. **章节编号**：现版缺第六~八章（第五章跳第九章），重制版按现结构保留还是顺延重排？
